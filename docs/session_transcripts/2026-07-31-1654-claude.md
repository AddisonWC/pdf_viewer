## The bug

`fitz.open(path)` doesn't read the file; MuPDF parses lazily and keeps reading from disk all session. An already-open `Document` survives a rename (its fd follows the inode), which is why this looked intermittent — but the viewer opens a **fresh** `Document` per render worker thread, lazily, on that thread's first task, plus one per copy window. Those go through the path, so the first page rendered on a cold thread after a move died with `no such file`. Rewrite-in-place (LaTeX recompiling a paper you're reading) was worse: no error, just a live `Document` reading objects out of a file whose offsets all moved.

`_ThreadDocs` is now `_DocumentSource` (`pdfviewer.py:633`), which owns the bytes; the main thread, every worker, and every copy window get their `Document` from that one buffer.

## Why the read runs in the background

A synchronous slurp would have traded the bug for something worse. Your disk reads cold at **~25 MB/s** (btrfs zstd, NVMe scheduler `none`, /home 95% full) and your library has 300–660 MB scans — `Mcdonald;Weiss--Analysis_2012.pdf` is 664 MB. Reading that up front is a 27-second freeze with no window on screen. So the reader opens by path and is usable immediately, a daemon thread reads the file, and everything handed out afterwards comes off the buffer.

Two measurements drove the details:

- **A single big background `read()` starves the whole app.** Cold, 321 MB, foreground = open + TOC + render two pages: **1.65 s** alone, **12.53 s** against an unchunked background read, **1.63 s** against 1 MB chunks with 10 ms breathers — and the background read finishes in the same ~12.6 s either way. One huge read monopolises the device queue; the viewer's small page reads queue behind it. No trade-off to tune, both ends are best-case.
- **PyMuPDF shares an immutable stream buffer but copies a mutable one.** A `bytearray` gets copied per `Document` (321 MB → 674 MB RSS for one). So the read `readinto`s a bytearray and publishes `memoryview(buf).toreadonly()` — shared across all Documents, and peak RAM stays at 1× the file instead of the 2× a `b"".join` of chunks would need.

Net on the 664 MB scan, cold cache: window **1.02 → 1.60 s**, first page **3.34 → 4.05 s**, page jumps **228–301 ms → 38–78 ms** once buffered, RSS **195 → 831 MB**. You pay half a second of startup and the file's size in RAM; you get 3–6× faster navigation for the rest of the session.

The load window is the one genuinely racy moment, so it's closed too: the read consumes a handle opened in `__init__` (survives rename *and* unlink), and a `Document` requested after the path is gone but before the buffer lands falls back to `/proc/self/fd/N`, which still resolves to the unlinked inode. The status-overlay loading dot now stays lit while the slurp runs.

## Assistant (final reply) — 2026-07-31 17:23:13 PDT

The raw PDF file bytes — a verbatim copy of what's on disk, nothing decoded.

`_DocumentSource._data` is the result of reading the file into a buffer and freezing it as a read-only memoryview. It's byte-for-byte identical to the file: still-compressed content streams, still-compressed embedded images (JPEG/JBIG2/CCITT in a scan), fonts, the xref. MuPDF parses it lazily exactly as it did when reading from disk — the only thing that changed is *where* those reads are served from. So for the 664 MB textbook, the buffer is 664 MB, not the ~50 GB those page images would occupy decoded.

There are three separate memory pools in play, and only the first one is new:

1. **The file buffer** — 1× file size, shared by every `Document` and every window of that PDF (this is what the read-only memoryview buys; a mutable buffer would have been copied per `Document`).
2. **MuPDF's per-`Document` state** — parsed page trees plus its internal store of decoded glyphs/images. Small and lazy: four extra Documents over a 13 MB PDF added ~4 MB combined.
3. **The pixmap LRU** (`_pixmap_cache`) — the actual rendered page images as `QPixmap`s at screen resolution. This one *is* decoded pixels, and it long predates today's change; it's byte-budgeted at 256 MB (`_PIXMAP_CACHE_BUDGET_BYTES`) with oldest-first eviction.

That accounts for the 831 MB RSS on the big scan: 664 MB of file bytes, and ~167 MB of Qt plus MuPDF structures plus whatever pages were rendered.

The practical consequence is that the win is on I/O, not decode. A page jump went from 228–301 ms to 38–78 ms because fetching the page's compressed data became a memcpy instead of a cold btrfs read — but the JPEG/JBIG2 decode and the rasterization still happen per render, at the same cost as before. That's also why the residual GIL stall on image-heavy pages (from `page.get_pixmap()`) is untouched by this change: that cost is decode, and decode was never the thing waiting on disk.
