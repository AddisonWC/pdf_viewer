Overall, this is an unusually thoughtful personal PDF viewer. Rendering, mixed-DPI handling, cropping, navigation, and regression coverage show substantial real-world tuning. All 32 headless test groups passed in about 21 seconds, and compilation succeeded.

The main issues I found:

1. Search has an async race. Escaping an in-progress search does not invalidate its result ([pdfviewer.py](/home/addwc/a/study_tech/pdf_viewer/pdfviewer.py:3234)). A late result is still accepted and can navigate after the search box closes ([pdfviewer.py](/home/addwc/a/study_tech/pdf_viewer/pdfviewer.py:3251)). I reproduced this: the hidden search repopulated matches and jumped to page 6. This is the first thing I would fix and add a regression test for.

2. The viewer unconditionally forces Wayland ([pdfviewer.py](/home/addwc/a/study_tech/pdf_viewer/pdfviewer.py:21)). That makes the default entry point unsuitable for X11, Windows, macOS, and some remote/headless environments. If this is intentionally GNOME/Wayland-only, document it; otherwise let Qt select the platform or only force Wayland when `WAYLAND_DISPLAY` exists.

3. Encrypted PDFs are not handled as the startup comment claims ([pdfviewer.py](/home/addwc/a/study_tech/pdf_viewer/pdfviewer.py:981)). PyMuPDF opens them successfully, but page loading later fails. The result is a window full of render errors rather than a password prompt or clean “unsupported” message.

4. `Ctrl+N` is not quite an “exact duplicate.” Construction immediately renders and starts a fresh random content-crop detection ([pdfviewer.py](/home/addwc/a/study_tech/pdf_viewer/pdfviewer.py:1823)); `open_copy()` then changes the page and renders again without copying the current crop ([pdfviewer.py](/home/addwc/a/study_tech/pdf_viewer/pdfviewer.py:2912)). This wastes work and can give the copy a different zoom.

5. Memory can become substantial: the entire PDF is retained in RAM, plus a 256 MB pixmap cache per window ([pdfviewer.py](/home/addwc/a/study_tech/pdf_viewer/pdfviewer.py:790)). A 600 MB scan with several copy windows could exceed a gigabyte quickly.

My broader improvement priorities would be:

- Add a README covering installation, platform scope, controls, optional Claude integration, and the test command.
- Add version ranges or a lock file; [requirements.txt](/home/addwc/a/study_tech/pdf_viewer/requirements.txt:1) is currently completely unpinned.
- Split the 4,183-line module into rendering/document, crop detection, search, integrations, and UI modules.
- Convert the test harness to pytest and add cases for async cancellation, encrypted PDFs, platform selection, and copy-window zoom state.
- Make state writes atomic; the current direct JSON overwrite can lose all saved positions if interrupted ([pdfviewer.py](/home/addwc/a/study_tech/pdf_viewer/pdfviewer.py:238)).

The core is strong. It feels more like a mature, performance-tuned power-user application than the “minimal viewer” its description suggests.
