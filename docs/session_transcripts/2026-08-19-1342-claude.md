## On the GitHub sharing — what I think

### The Ask-AI feature is the interesting design problem, and it's smaller than it looks

Right now it's four hard-wired things: `gnome-terminal`, the `claude` binary, `--model sonnet --effort high`, and a vendor-specific prompt file. Your instinct is right that people will want different agents and logins — but note that **logins aren't actually your problem**. The launcher shells out to whatever CLI the user already has authenticated. There's no key handling, no account coupling, nothing of yours to leak. That's a real advantage of the fire-and-forget design you chose, and it means the sharing question is purely "how do people configure the command," not "how do we handle credentials."

The shape I'd argue for is a config file with a command template:

```toml
[ask_ai]
terminal = "auto"          # or an explicit argv
command = ["claude", "--model", "sonnet", "--effort", "high",
           "--append-system-prompt-file", "{prompt_file}", "{initial}"]
prompt_file = "pdf_helper_prompt.txt"
```

Someone using a different agent swaps `command`; someone with a different prompt swaps `prompt_file`. `terminal = "auto"` probes a list (`gnome-terminal`, `konsole`, `xfce4-terminal`, `alacritty`, `kitty`, `x-terminal-emulator`) — that's the Ubuntu-relevant half, since Ubuntu GNOME has `gnome-terminal` but Kubuntu and most tiling setups don't.

The part I'd push back on: **`pdf_helper_prompt.txt` is more valuable than the launcher and is nearly vendor-neutral already.** The claims in it — notation doesn't survive text extraction, so read page images; localize by keyword then read; watch for printed-vs-physical page offset — are true of any vision-capable model. That's the actual intellectual content of the feature and it ships fine as-is. The `--append-system-prompt-file` flag is Claude Code-specific, but the file's *content* isn't.

One caveat worth deciding on: the feature currently reads as "Ask Claude" in the help page, the overlay, and the function names. If it's becoming generic, that's a rename with about a dozen touch points, and it's much cheaper to do before people have muscle memory than after.

### Hotkeys — configurable and default-cleanup are separable, do them in that order

You mentioned both. They're independent, and the config layer should come first, because once bindings live in a table rather than in `_install_shortcuts()`, changing the defaults is a one-line diff instead of a hunt across three files.

The three-way sync problem is the real design constraint here: `bind(...)` → `HELP_HTML` → now `docs/HOTKEYS.md`. That's already bitten this project (the 2026-07-28 entry notes the help page "will silently drift"). A single binding table with an action name + description per entry would let Ctrl+H be *generated*, collapsing three sources to one. That's a genuine simplification, not just a config feature.

Two constraints from GOTCHAS that a config layer has to respect, and which will surprise whoever implements it:

- `?` can't go through `QShortcut` at all — shifted characters must be matched in `eventFilter`. So the config layer needs two dispatch paths, not one.
- You can't alias an already-bound sequence with a second `QShortcut` (Qt calls it ambiguous and fires *neither*). A naive "user adds a binding" feature will silently break the key it collides with. The table needs collision detection at load time — and per your own no-silent-no-op rule, it should say something visible when it finds one.

On the defaults themselves: the doubled aliases (`0`/`B`, `C`/`M`, `T`/`;`) are the obvious cleanup, but I'd flag `Q` quitting with no modifier and no confirmation as the one that will actually bite a stranger.

### Getting it onto your colleague's Ubuntu box

The blockers, roughly in order of how likely they are to bite:

1. **`QT_QPA_PLATFORM` defaults to `wayland`.** Ubuntu 22.04 defaults to Wayland but 24.04 users on NVIDIA frequently run X11, and either way an X11 session with this forced will fail to start. The fix the reviewer suggests is right and small: only prefer Wayland when `WAYLAND_DISPLAY` is set, otherwise let Qt choose.
2. **`requirements.txt` is completely unpinned**, and your venv is Python 3.14 / PySide6 6.11 — well ahead of Ubuntu's system Python. A colleague on 22.04 (Python 3.10) will resolve to different PySide6 and PyMuPDF versions than you've tested against. PyMuPDF is the riskier one, since the content-detection code leans on `get_bboxlog()` kind strings, which are MuPDF-internal and not a stability guarantee.
3. **`gnome-terminal`** — covered above.

None of these are hard. But (2) is the one where "works on my machine" is doing the most load-bearing work right now.

### Repo hygiene before `git init`

`venv/` and `__pycache__/` obviously want gitignoring. `.claude/settings.local.json` should be too — it's local permission grants, and it currently contains a stale absolute path from an earlier directory name. Worth a decision rather than a default: **`addison_notes.txt` is your personal working queue**, and it'll be visible to everyone you share with. The 200KB of test PDFs are fine to keep; they're real fixtures.

### What I'd fix before other people run it

From the review, two are sharing-relevant rather than nice-to-have:

- **The search async race** (escaping an in-flight search still lets the result navigate). Reproducible, and it's exactly the kind of thing that makes a new user distrust the tool.
- **Atomic state writes.** The last-read-page JSON is overwritten directly, so an interrupted write loses *every* saved position. On your own machine that's an annoyance you'd recover from; on someone else's it's the tool eating their data.

Encrypted PDFs failing with a wall of render errors rather than a clean message is also a first-impressions issue, though a rarer one.

## Multi-agent project conventions

The short version: **Codex reads `AGENTS.md`, Claude Code reads `CLAUDE.md`**, and other tools have their own (Cursor's `.cursor/rules`, Gemini's `GEMINI.md`). `AGENTS.md` has become the closest thing to a cross-tool standard — it's an open convention specifically meant to stop this proliferation, and Codex uses it natively.

Three patterns people actually use:

1. **`AGENTS.md` is the real file; `CLAUDE.md` is a symlink to it.** Zero duplication, one source of truth. Git stores symlinks fine. The wart is Windows, where symlinks need a config flag to check out properly — irrelevant if this stays Linux-only, which you said it mostly will.
2. **`AGENTS.md` is the real file; `CLAUDE.md` is a one-line pointer** (`See AGENTS.md`). Costs one extra file read, works everywhere, no symlink weirdness. This is the most common choice.
3. **Both entry files stay thin; the substance lives in tool-neutral docs.**

The organizing principle underneath all three, and the one that actually matters: **the entry file should contain only what's about agent *behavior*; everything factual goes in ordinary documentation.** An architecture doc, a gotchas list, a devlog — those are just good project docs. They're useful to a human colleague reading the code, and no agent needs a special filename to be told to read them.

That's already how I structured the merge, which was partly luck and partly the point. `docs/` is entirely tool-neutral prose — nothing in it says "Claude" except where it's describing the Ask-AI feature, which genuinely is about Claude Code.
